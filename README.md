# ИИ-агент исполнительной документации

Локальный MVP `selected-template-v2`: специалист выбирает один
зарегистрированный Excel-шаблон на фронте, загружает один PDF проекта, а агент
переносит подтверждённые сведения в этот шаблон и возвращает один черновой XLSX.

Модель извлекает и сопоставляет факты, но никогда не выбирает шаблон или
структуру книги. Серверный контракт заранее фиксирует имя результата и белый
список ячеек; модель может предложить значения только для этих целей, а Python
отклоняет произвольные координаты и ограниченно патчит OOXML. Пропущенные,
конфликтующие или ненадёжные значения остаются пустыми и получают заметную
заливку. Критичные пропуски переводят задание в `NEEDS_INPUT` и блокируют
финальный выпуск, но помеченный черновик остаётся доступен специалисту.

Утверждённые legacy-контракты АОСР КЛ-0,4 кВ, КЛ-6 кВ и ВРЩ сохраняются для
регрессии. В новом интерактивном флоу каждая книга запускается отдельно.

## Запуск

```bash
cp .env.example .env
# заполнить OPENAI_API_KEY; модели и лимиты уже имеют экономичные значения
uv sync --extra dev
uv run uvicorn --app-dir src executive_docs.main:app --host 127.0.0.1 --port 8000
```

Открыть `http://127.0.0.1:8000`.

Требуются Python 3.12 и LibreOffice (`soffice`). Путь к LibreOffice можно задать через `SOFFICE_PATH`.

Для локальной проверки без API установить `AGENT_MODE=heuristic`. Этот режим проверяет flow и `NEEDS_INPUT`, но не заменяет модельный анализ проекта.

## CI/CD

Workflow `.github/workflows/ci-cd.yml` запускает тесты на каждый `push` и
`pull_request`. После успешных тестов коммит из ветки `main` автоматически
разворачивается на сервере; деплой также можно запустить вручную через
`workflow_dispatch`.

В GitHub в `Settings → Secrets and variables → Actions` должны быть созданы
два Repository Secret:

- `SSH_PRIVATE` — полный приватный SSH-ключ, публичная часть которого добавлена
  на сервере в `~/.ssh/authorized_keys`;
- `DOTENV` — полное содержимое рабочего `.env`, созданного из `.env.example`,
  включая заполненные `SSH_USER` и `SERVER_IP`.

На сервере должны быть установлены Docker Engine и плагин Docker Compose, а
пользователь `SSH_USER` должен иметь право запускать `docker compose` без
интерактивного `sudo`. Приложение разворачивается в `~/energo_PVO`. Каталоги
`data/` и `templates/approved/` не удаляются при следующих деплоях.
До первого рабочего запуска специалист должен поместить зарегистрированные
кандидаты и утверждённые шаблоны в `~/energo_PVO/templates/approved/` согласно
их контрактам. CI может создавать технические кандидаты только как временные
тестовые фикстуры и никогда не утверждает их для production.
Для уже утверждённых контрактов контейнер `template-init` восстанавливает
отсутствующие эталонные XLSX из образа, предварительно полученные
детерминированной очисткой и проверяемые генератором по SHA-256. Существующие
файлы в `templates/approved/` он не перезаписывает.

Пять автоматически подготовленных книг из `NEW_TEMPLATES/` имеют статус
`DISCOVERY_REVIEW_REQUIRED`. Их whitelist ячеек ещё не утверждён специалистом,
поэтому они доступны только как проверочные черновики и не могут перейти в
финальный выпуск. Из кандидатов удалены OOXML-кэши внешних связей, лишние
shared strings, пользовательские части и прежние метаданные документа.
При этом `emr` и `aosr_vl` всё ещё блокируются исходными `#REF!`, а `avk` и
`aosr_vl` — оставшимися формулами со ссылками на внешние книги. `ojr` и
`protocols` проходят текущую техническую проверку, но это не утверждает их
автоматически.

Docker Compose поднимает два явно именованных контейнера: `nginx` раздаёт
статические CSS/JS и проксирует запросы, `backend` запускает FastAPI и
LibreOffice только во внутренней сети Compose. Наружу контейнер `nginx`
публикуется на `${NGINX_HOST}:${NGINX_PORT}`; значения по умолчанию
`127.0.0.1:80` оставляют проект доступным только на сервере. Публикация на
`0.0.0.0` разрешена только за отдельным контуром аутентификации и TLS.
Максимальный размер запроса к Nginx задаётся через
`NGINX_CLIENT_MAX_BODY_SIZE`.

При создании задания специалист сначала выбирает один зарегистрированный
серверный шаблон, затем загружает ровно один рабочий проект PDF. Пользователь не
загружает XLSX с датами, паспортами или другими фактическими сведениями и не
загружает сам шаблон. Другой шаблон оформляется отдельным запуском.

За один проход приложение формирует один черновой XLSX из выбранного шаблона.
Найденные сведения записываются только в разрешённые контрактом цели.
Неподтверждённые даты, объёмы, паспорта/сертификаты, изменения, профили и другие
поля остаются пустыми и выделяются заливкой. В `NEEDS_INPUT` оператор видит
компактный список причин рядом со ссылкой на черновик. Selected-template MVP не
принимает дополнительные XLSX или ответы для автоматической догенерации:
специалист проверяет выделенные ячейки в единственном файле, а новый проход
запускает отдельным заданием. Пропуски блокируют финальное утверждение, но не
скачивание проверочного черновика.
SHA-256, UUID и внутренние файловые пути остаются в аудите и не выводятся в
пользовательском интерфейсе. Координаты незаполненных ячеек, напротив,
показываются специалисту, чтобы их было легко найти в Excel.

Эвристический режим намеренно не извлекает значения из PDF. Он нужен для
проверки загрузки, очереди, генератора, подсветки пропусков и валидаторов без
расхода API.

## Профили расхода и защита бюджета

При запуске задания специалист выбирает режим:

- `economy` — Luna, low reasoning и минимальный безопасный набор визуальных страниц;
- `balanced` — Terra, medium reasoning и выборочные страницы; режим по умолчанию;
- `quality` — Sol, high reasoning и расширенный визуальный контекст для сложного проекта.

До API приложение локально строит постраничный индекс единственного PDF в
`data/runs/<job-id>/extracted/`, повторно использует его по SHA-256 и перед
каждым чтением вновь сверяет исходный файл с хэшем. Выбранный XLSX, ETALON и
готовые книги в модельный контекст не передаются. Контракт выбранного шаблона
сужает список доступных модели смысловых полей, а страницы отбираются общим
индексатором и моделью; отдельной контрактной маршрутизации страниц пока нет.
Модель не расходует вызов на выбор книги. Страницы без надёжного текстового слоя имеют приоритет и
не отбрасываются ради экономии. Если обязательный визуальный набор не помещается
в профиль, обработка останавливается до API вместо скрытого исключения
источника.

В legacy-контуре после `NEEDS_INPUT` модель может получить сохранённые Claims и
ответы специалиста без повторной загрузки неизменившегося PDF. В
selected-template MVP выполняется один модельный проход. Перед каждым
Responses-вызовом
выполняется точный token preflight; если пакет превышает лимит, дублирующий
извлечённый текст автоматически сжимается, а обязательные визуальные страницы
сохраняются. Если точный подсчёт недоступен, обработка по умолчанию
останавливается до платного вызова. Локальную оценку можно явно разрешить через
`ALLOW_APPROXIMATE_TOKEN_PREFLIGHT=true`, но тогда токеновый предел становится
оценочным. По умолчанию действуют жёсткие лимиты 100 000 входных токенов на
вызов, 400 000 на всё задание и предварительный лимит $2 на всё задание по
зафиксированному снимку тарифов. Превышение не отключает проверки. Usage
сохраняется в SQLite после каждого платного ответа и входит в
`report.json`/`manifest.json`.

Модели и ограничения меняются через `.env`: `OPENAI_ECONOMY_MODEL`, `OPENAI_ANALYSIS_MODEL`, `OPENAI_REVIEW_MODEL`, `OPENAI_QUALITY_MODEL`, `MAX_INPUT_TOKENS_PER_CALL`, `MAX_JOB_INPUT_TOKENS`, `MAX_JOB_COST_USD` и `MAX_MODEL_CALLS_PER_JOB`. `OPENAI_MODEL` оставлен только для обратной совместимости.

## Реальный тест selected-template

1. Выбрать один из discovery-кандидатов и учитывать показанный на фронте статус.
2. Запустить приложение с `AGENT_MODE=openai` и рабочим `OPENAI_API_KEY`.
3. Выбрать одну книгу и указать специалиста.
4. Загрузить один основной PDF проекта.
5. Не загружать заполненные XLSX: они остаются материалом для слепого
   сравнения после генерации.
6. Первый проход должен вернуть один помеченный XLSX. Нехватка подтверждённых
   фактов даёт `NEEDS_INPUT`, а обнаруженный технический дефект книги —
   `FAILED_VALIDATION`.
7. Изучить XLSX и отчёт проверок; выделенные ячейки заполнить или подтвердить
   вне автоматического контура.
8. Для других книг создать отдельные задания с тем же PDF. Каждый запуск
   должен вернуть только выбранный workbook.
9. ETALON использовать только в отдельном регрессионном контуре. Сейчас
   регистрационный скрипт сравнивает с ним техническую структуру кандидата;
   blind-прогон `PDF → черновик → ETALON` ещё не реализован. Автоматическое
   утверждение выбранной книги в текущем MVP заблокировано.

Задания и их ревизии находятся в `data/runs/<job-id>/`. Предыдущая ревизия не перезаписывается.

Существующий CLI ниже остаётся legacy-регрессионным сценарием составного
project1 и не описывает пользовательский `selected-template-v2`:

```bash
uv run python scripts/run_project1_blind.py --mode heuristic --profile balanced --branch khimki --first-number 1
```

Команда печатает `job_id`; её результаты нельзя трактовать как один
пользовательский запуск нового флоу. Для настоящей интерактивной проверки
выбирайте одну книгу на фронте.

## Подготовка шаблонов

```bash
uv run python scripts/register_selected_templates.py
uv run python scripts/register_selected_templates.py --check
```

Первая команда заново создаёт очищенные discovery-кандидаты в
`templates/approved/` и их контракты в `templates/fill-contracts/`. Вторая
строит те же артефакты во временной папке и проверяет побайтовую
воспроизводимость, не перезаписывая зарегистрированные файлы.

Whitelist, подписи, типы и признак ручного поля выводятся только из структуры
`NEW_TEMPLATES/`: входных листов, формул, объединений и редактируемых областей.
Старые литералы очищаются, формульные ссылки на локальные листы по возможности
локализуются; внешние link-cache части, неиспользуемые shared strings,
пользовательские OOXML-данные и прежние свойства документа удаляются.
Отсутствие значения в рабочем черновике отмечается заливкой. Исходные книги не
изменяются.

Заполненные книги из `ETALON/` не участвуют в построении mapping и не
используются как проектные входы. Они подключаются только после подготовки
кандидата для записи регрессионных findings. Пять текущих кандидатов имеют
`approved: false` и статус `DISCOVERY_REVIEW_REQUIRED`: их whitelist ещё должен
проверить специалист, поэтому они создают только помеченный черновик и не могут
перейти в финальный выпуск.

Текущий discovery-контракт фиксирует координату, подпись, тип значения,
обязательность и признак ручного подтверждения. До статуса `APPROVED` специалист
должен дополнить его стабильными смысловыми ID, правилами повторяемых диапазонов
и ожидаемыми параметрами видимости/рендера. Отсутствие этих сведений не мешает
получить проверочный черновик, но является отдельной причиной не считать
кандидат production-шаблоном.

`ETALON/` используется только отдельным регрессионным контуром. Текущий
регистрационный скрипт сравнивает уже подготовленный кандидат с соответствующей
книгой ETALON и записывает технические findings; автоматического blind-прогона
записанного PDF через модель с последующим семантическим сравнением пока нет.
Значения из ETALON не передаются модели, не становятся Claims, профилями,
правилами или доказательством утверждения шаблона. Формульные ошибки, внешние
связи, отличия видимости и порядка листов в ETALON фиксируются как findings, а
не копируются.

`scripts/qualify_templates.py` и `scripts/approve_template.py` относятся к
legacy-контрактам. Они не утверждают контракты из `templates/fill-contracts/`.
Отдельный контур утверждения новых selected-template кандидатов в этом MVP
намеренно не реализован: успешные тесты, техническая чистота и наличие ETALON
не заменяют явного решения специалиста.

Каталог `data/runs/` содержит локальные результаты прогонов и не коммитится.

## Профили организации и филиалов

Файлы `profiles/organization.yaml`, `profiles/khimki.yaml` и `profiles/solnechnogorsk.yaml` заполнены найденными кандидатами, но имеют `approved: false`. Значения из старых книг не используются автоматически. Специалист проверяет реквизиты, ФИО, должности, приказы и периоды полномочий, заполняет пропуски, затем выполняет:

```bash
uv run python scripts/approve_profile.py \
  --profile solnechnogorsk \
  --version 1.0 \
  --approved-by "ФИО" \
  --effective-from 2026-01-01 \
  --effective-to 2026-12-31
```

Организация утверждается такой же командой с `--profile organization`. Профиль вне периода фактических работ блокирует выпуск.

## Состояния и API

Путь selected-template:
`FILES_UPLOADED → ANALYZING → GENERATING → VALIDATING → NEEDS_INPUT | FAILED_VALIDATION`.
В обоих конечных состояниях один черновик может оставаться доступным:
`NEEDS_INPUT` означает нехватку подтверждённых фактов, а
`FAILED_VALIDATION` — технический блокер книги. Повторное заполнение
`NEEDS_INPUT` через API в текущем MVP отсутствует; для другого шаблона или
нового набора подтверждённых данных создаётся новое задание.

Legacy-путь с вопросами, ревизиями и `READY_FOR_REVIEW → APPROVED_FINAL`
сохраняется отдельно.

- `GET /api/templates` — безопасный публичный каталог зарегистрированных
  серверных шаблонов и их статусов без путей, SHA и cell mappings;
- `POST /api/jobs` — multipart: обязательный стабильный `template_id`, один
  PDF в поле `files` и параметры оператора; XLSX-вход и второй PDF отклоняются;
- `/kits/<номер>` и `/api/kits/<номер>` — пользовательские маршруты без UUID;
- `GET /api/jobs/{id}` — состояние и доказательства;
- `POST /api/jobs/{id}/answers` — подтверждённые ответы только для legacy;
  selected-template отвечает `409`;
- `POST /api/jobs/{id}/draft-excel` — повторная генерация только для legacy;
  selected-template отвечает `409`;
- `GET /api/jobs/{id}/draft-excel/0` — скачать единственный сформированный XLSX;
- `GET /api/jobs/{id}/preview` — PDF текущей ревизии;
- `POST /api/jobs/{id}/retry` — повтор анализа после `FAILED_ANALYSIS`, а для
  selected-template также генерации после `FAILED_GENERATION`;
- `POST /api/jobs/{id}/review` — legacy-подтверждение/исправление; для
  selected-template утверждение и ревизия заблокированы, отмена разрешена;
- `GET /api/jobs/{id}/download` — только утверждённый ZIP;
- `GET /api/corrections` — предложения для базы знаний;
- `POST /api/corrections/{id}/review` — ручное решение по предложению.

Customer/global-исправление нельзя утвердить без подтверждённого регрессионного прогона. Утверждение proposal не меняет скилл автоматически.

`template_id`, версия, SHA-256 кандидата и SHA-256 полного контракта
закрепляются при создании задания. Для другого шаблона создаётся новое задание.
Даже если PDF содержит несколько семейств документов, агент не добавляет второй
workbook. В selected-template контуре логический план — это закреплённый
контракт плюс проверенный набор назначений «поле → значение и страница PDF»;
legacy-массив `document_plans` здесь не создаётся.

## Безопасность MVP

Локальный запуск по умолчанию использует `127.0.0.1` и не содержит
авторизации; публичный Compose-деплой требует отдельного защищённого контура.
Исходный PDF и серверные шаблоны не изменяются. Публичный `template_id`
разрешается только через реестр и не является файловым путём. PDF проверяется
по расширению, сигнатуре и структуре; XLSX от пользователя не принимается.
Универсальный файловый маршрут выдаёт только PDF-предпросмотры текущей ревизии;
исходный PDF и внутренние отчёты через него недоступны.
Текст внутри PDF всегда считается данными, а не инструкциями агенту. В режиме
`openai` выбранные страницы PDF и PDF-предпросмотр передаются в OpenAI API;
шаблон и ETALON не передаются. Временные File API-объекты удаляются после
вызова, а Responses создаются с `store=false`.
