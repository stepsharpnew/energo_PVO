# ИИ-агент исполнительной документации

Локальный MVP: загрузка исходных файлов, анализ OpenAI Responses API, `NEEDS_INPUT`, заполнение АОСР КЛ-0,4 кВ / КЛ-6 кВ / ВРЩ, проверка и итоговый ZIP.

Модель определяет состав работ, сопоставляет источники и строит семантический план. Python ограниченно читает файлы, патчит только разрешённые ячейки OOXML, рендерит PDF, выполняет проверки и собирает архив. Критичные значения без источника не допускаются.

## Запуск

```bash
cp .env.example .env
# заполнить OPENAI_API_KEY; модели и лимиты уже имеют экономичные значения
uv sync --extra dev
uv run uvicorn --app-dir src executive_docs.main:app --host 127.0.0.1 --port 8000
```

Открыть `http://127.0.0.1:8000`.

Требуются Python 3.12 и LibreOffice (`soffice`). Путь к LibreOffice можно задать через `SOFFICE_PATH`.

Для локальной проверки без API установить `AGENT_MODE=heuristic`. Этот режим проверяет flow и `NEEDS_INPUT`, но не заменяет модельный анализ проекта.

## CI/CD

Workflow `.github/workflows/ci-cd.yml` запускает тесты на каждый `push` и
`pull_request`. После успешных тестов коммит из ветки `main` автоматически
разворачивается на сервере; деплой также можно запустить вручную через
`workflow_dispatch`.

В GitHub в `Settings → Secrets and variables → Actions` должны быть созданы
два Repository Secret:

- `SSH_PRIVATE` — полный приватный SSH-ключ, публичная часть которого добавлена
  на сервере в `~/.ssh/authorized_keys`;
- `DOTENV` — полное содержимое рабочего `.env`, созданного из `.env.example`,
  включая заполненные `SSH_USER` и `SERVER_IP`.

На сервере должны быть установлены Docker Engine и плагин Docker Compose, а
пользователь `SSH_USER` должен иметь право запускать `docker compose` без
интерактивного `sudo`. Приложение разворачивается в `~/energo_PVO`. Каталоги
`data/` и `templates/approved/` не удаляются при следующих деплоях.
До первого рабочего запуска специалист должен поместить уже утверждённые
шаблоны в `~/energo_PVO/templates/approved/`; CI создаёт очищенные кандидаты
только как временные тестовые фикстуры и не утверждает их для production.
Для уже утверждённых контрактов контейнер `template-init` восстанавливает
отсутствующие эталонные XLSX из образа, предварительно полученные
детерминированной очисткой и проверяемые генератором по SHA-256. Существующие
файлы в `templates/approved/` он не перезаписывает.

Docker Compose поднимает два явно именованных контейнера: `nginx` раздаёт
статические CSS/JS и проксирует запросы, `backend` запускает FastAPI и
LibreOffice только во внутренней сети Compose. Наружу контейнер `nginx`
публикуется на `${NGINX_HOST}:${NGINX_PORT}`; значения по умолчанию
`0.0.0.0:80` открывают проект по HTTP на публичном IP сервера. Максимальный
размер запроса к Nginx задаётся через `NGINX_CLIENT_MAX_BODY_SIZE`.

При создании задания обязателен только рабочий проект PDF. Таблица фактических
данных XLSX и остальные приложения опциональны; если критичного факта нет в
загруженных источниках, задание переходит в `NEEDS_INPUT`.

В `NEEDS_INPUT` оператор видит только необязательные текстовые поля и выбор
`Да/Нет` для состояния изменений. Частично заполненная форма сохраняется без
обязательного заполнения всех полей и без повторного модельного вызова, если
состав книг и листов уже определён первым анализом. После отправки приложение
формирует черновые XLSX из утверждённых шаблонов: найденные сведения
записываются в разрешённые контрактом ячейки, а неподтверждённые даты, объёмы,
паспорта/сертификаты, изменения и профили явно помечаются внутри Excel.
Пропуски блокируют только финальное утверждение и ZIP. SHA-256, UUID и
внутренние идентификаторы остаются в аудите, но не выводятся в пользовательском
интерфейсе.

Эвристический режим намеренно не может перейти в `READY_FOR_REVIEW`: независимая модельная проверка обязательна. Он нужен для проверки загрузки, очереди, вопросов, генератора и валидаторов без расхода API.

## Профили расхода и защита бюджета

При запуске задания специалист выбирает режим:

- `economy` — Luna, low reasoning и минимальный безопасный набор визуальных страниц;
- `balanced` — Terra, medium reasoning и выборочные страницы; режим по умолчанию;
- `quality` — Sol, high reasoning и расширенный визуальный контекст для сложного проекта.

Все загруженные файлы остаются в инвентаризации. До API приложение локально строит постраничный/полистовой индекс в `data/runs/<job-id>/extracted/`, повторно использует его по SHA-256 и перед каждым чтением вновь сверяет исходный файл с хэшем. Из платного контекста исключаются явно непилотные КТП, ВЛ, GEO, GNB, AVK и EMR. Во всех профилях проект передаётся как текст выбранных страниц и как ограниченный PDF-срез: страницы без надёжного текстового слоя имеют приоритет и не отбрасываются ради экономии. Все страницы пилотной исполнительной схемы считаются обязательным визуальным минимумом. Если обязательный набор не помещается в профиль, обработка останавливается до API вместо скрытого исключения источника. Выбор не зависит от порядка загрузки файлов.

После `NEEDS_INPUT` модель получает сохранённые Claims и ответы специалиста без повторной загрузки неизменившихся PDF. Перед каждым Responses-вызовом выполняется точный token preflight; если первичный пакет превышает лимит, дублирующий извлечённый текст автоматически сжимается, а обязательные визуальные страницы сохраняются. Если точный подсчёт недоступен, обработка по умолчанию останавливается до платного вызова. Локальную оценку можно явно разрешить через `ALLOW_APPROXIMATE_TOKEN_PREFLIGHT=true`, но тогда токеновый предел становится оценочным. По умолчанию действуют жёсткие лимиты 100 000 входных токенов на вызов, 400 000 на всё задание и предварительный лимит $2 на всё задание по зафиксированному снимку тарифов. При расчёте резервируется максимально разрешённый ответ. Неизвестная модель блокируется при включённом USD-лимите. Превышение не отключает проверки. Usage сохраняется в SQLite сразу после каждого платного ответа; фактические input/cached/cache-write/output/reasoning tokens и оценка USD отображаются в задании и входят в `report.json`/`manifest.json` вместе с датой снимка тарифов.

Модели и ограничения меняются через `.env`: `OPENAI_ECONOMY_MODEL`, `OPENAI_ANALYSIS_MODEL`, `OPENAI_REVIEW_MODEL`, `OPENAI_QUALITY_MODEL`, `MAX_INPUT_TOKENS_PER_CALL`, `MAX_JOB_INPUT_TOKENS`, `MAX_JOB_COST_USD` и `MAX_MODEL_CALLS_PER_JOB`. `OPENAI_MODEL` оставлен только для обратной совместимости.

## Реальный тест project1

1. Утвердить очищенные пилотные шаблоны и профили филиалов.
2. Запустить приложение с `AGENT_MODE=openai` и рабочим `OPENAI_API_KEY`.
3. Создать задание «Химки» и указать первый номер АОСР.
4. Загрузить основной PDF проекта и все PDF исполнительных схем из `project1/`: локальный индекс сам отфильтрует непилотные источники из платного контекста, но сохранит их в инвентаризации.
5. Не загружать три заполненных XLSX: они остаются материалом для слепого сравнения.
6. Первый проход должен вернуть `NEEDS_INPUT` по фактическим датам, паспортам/сертификатам, изменениям и неутверждённому профилю.
7. Передать только подтверждённые сведения. После генерации изучить PDF и отчёт проверок.
8. Сравнить результат с экспертно очищенным golden set. Только специалист нажимает подтверждение финального комплекта.

Задания и их ревизии находятся в `data/runs/<job-id>/`. Предыдущая ревизия не перезаписывается.

Быстрая подготовка слепого задания без API и без заполненных Excel:

```bash
uv run python scripts/run_project1_blind.py --mode heuristic --profile balanced --branch khimki --first-number 1
```

Команда печатает `job_id`; запустите веб-приложение и откройте это задание из списка. Для настоящего анализа используйте `--mode openai` после настройки ключа.

## Подготовка шаблонов

```bash
uv run python scripts/qualify_templates.py
```

Команда создаёт отчёт о дефектах и контрольные суммы, не меняя исходные файлы. Найденные `#REF!`, внешние ссылки и старые данные не исправляются автоматически.

После ручной очистки и проверки специалист регистрирует конкретный файл:

```bash
uv run python scripts/approve_template.py \
  --template-id aosr_kl_6 \
  --clean-file /путь/к/очищенному.xlsx \
  --version 1.0 \
  --approved-by "ФИО" \
  --notes "Проверены формулы, печать и старые значения"
```

До этого контракт имеет `approved: false`, а выпуск закономерно завершится `FAILED_VALIDATION` с кодом `TEMPLATE_NOT_APPROVED`.

Отчёт квалификации создаётся в
`data/runs/template-maintenance/qualification-report.json`. Он фиксирует ошибки
формул и именованных диапазонов в шаблоне КЛ, а также формульные ошибки и внешние
ссылки в шаблоне ВРЩ. Каталог `data/runs/` содержит локальные результаты прогонов
и не коммитится.

## Профили организации и филиалов

Файлы `profiles/organization.yaml`, `profiles/khimki.yaml` и `profiles/solnechnogorsk.yaml` заполнены найденными кандидатами, но имеют `approved: false`. Значения из старых книг не используются автоматически. Специалист проверяет реквизиты, ФИО, должности, приказы и периоды полномочий, заполняет пропуски, затем выполняет:

```bash
uv run python scripts/approve_profile.py \
  --profile solnechnogorsk \
  --version 1.0 \
  --approved-by "ФИО" \
  --effective-from 2026-01-01 \
  --effective-to 2026-12-31
```

Организация утверждается такой же командой с `--profile organization`. Профиль вне периода фактических работ блокирует выпуск.

## Состояния и API

Основной путь: `FILES_UPLOADED → ANALYZING ↔ NEEDS_INPUT → GENERATING → VALIDATING → READY_FOR_REVIEW → APPROVED_FINAL`.

- `POST /api/jobs` — multipart-загрузка;
- `/kits/<номер>` и `/api/kits/<номер>` — пользовательские маршруты без UUID;
- `GET /api/jobs/{id}` — состояние и доказательства;
- `POST /api/jobs/{id}/answers` — подтверждённые ответы;
- `GET /api/jobs/{id}/preview` — PDF текущей ревизии;
- `POST /api/jobs/{id}/review` — подтверждение, исправление или отмена;
- `GET /api/jobs/{id}/download` — только утверждённый ZIP;
- `GET /api/corrections` — предложения для базы знаний;
- `POST /api/corrections/{id}/review` — ручное решение по предложению.

Customer/global-исправление нельзя утвердить без подтверждённого регрессионного прогона. Утверждение proposal не меняет скилл автоматически.

## Безопасность MVP

Приложение запускается только на `127.0.0.1` и не содержит авторизации. Не публикуйте его на `0.0.0.0`. Исходники не изменяются; имена вложений нормализуются; Office-файлы проверяются как OOXML и ограничиваются по распакованному размеру. Текст внутри загруженных документов всегда считается данными, а не инструкциями агенту. В режиме `openai` выбранные исходники и PDF-превью передаются в OpenAI API; временные File API-объекты удаляются после вызова, а Responses создаются с `store=false`.
